# Repository top-level layout

This document is hand written. It was created by the OpenSpec change
`catalogue-repo-layout`, step 1.1, and confirmed against a live `ls -a`,
`git ls-files`, and `git check-ignore -v` run on 2026-08-19 rather than
copied from an earlier survey. A later run of this repository's own
regeneration tooling does not touch this file; if the top-level listing
changes, a person updates this table by hand.

Git status is one of: `tracked` (git ls-files lists it), `ignored`
(git check-ignore reports a rule), or `untracked-visible` (neither: it
would show as a bare `??` in `git status --porcelain` with no ignore
rule covering it). Disposition is one of `keep`, `ignore`, `delete`,
`decide`.

## Tracked files referencing paths a fresh clone will not have

Step 4.2 grepped every tracked configuration and script file for path-shaped
strings, then checked each in-repository path with `git check-ignore -v`.
Two of the seven cases below are genuinely covered by this repository's own
`.gitignore`; the requirement text in the spec is about that case. The other
five sit outside `.gitignore`'s reach entirely, either because the path is
absolute and points outside the repository, or because the referenced file
is generated output that does not need to exist until the tool that reads
it also produced it. All seven are recorded here because each one breaks a
fresh clone on a different machine, whether or not `.gitignore` is the
mechanism responsible.

None of the seven has a fix as small as step 4.1's removal of the `time.ps1`
ignore rule. Tracking `target/debug/deepseek-custom.exe` or
`.quality/units.json` would mean checking in build output and scanner
output, gigabytes and machine-specific artifacts respectively, which the
project's own conventions (see `CLAUDE.md`, "A process that generates a
file keeps that file out of git") rule out on sight. Rewriting the two
absolute paths under `C:\Users\siriu\...` to something portable is a real
fix, but it touches `settings.json` (an autopilot task prompt, itself a
save file the GUI rewrites) and `scripts/quality-checklist.mjs`, both of
which this step's briefing lists as leave-alone. So every case below stays
open as a catalogue row rather than a patch.

Case 1. `run.ps1` names `target\debug\deepseek-custom.exe` under
`$projectRoot`. Confirmed ignored: `git check-ignore -v run.ps1` was not
useful directly since the reference is a string inside the file rather
than a path git resolves from that file, but `git check-ignore -v
target/debug/deepseek-custom.exe` returns `.gitignore:1:/target`. This is
the correct, unavoidable shape for a launcher script: the executable is
cargo's own build output, created by `cargo build`, and re-created on every
build. A fresh clone runs `cargo build` first, same as the project's own
Build and Test section already says, and after that the path exists. Not a
defect, recorded so the row exists.

Case 2. `settings.json`'s autopilot task text names `.quality/units.json`
as both an input to `scripts/quality-checklist.mjs` and an output of the
scanner command two lines above it in the same prompt. Confirmed ignored:
`git check-ignore -v .quality/units.json` returns `.gitignore:41:.quality/`,
the same rule the table above cites for the `.quality` directory itself.
This is scanner output, written by the `node quality-scan.mjs ... >
.quality/units.json` command in the same prompt before
`quality-checklist.mjs` reads it back. Same shape as case 1: generated,
then consumed, in a documented order, inside one autopilot task prompt.

Case 3. `scripts/quality-checklist.mjs` also names `.quality/units.json`,
in its header comment and in the regeneration instructions it prints into
`docs/notes/quality-checklist.md`. Same file, same reasoning as case 2.

Case 4. `settings.json`'s autopilot task text names an absolute path,
`C:\Users\siriu\.claude\plugins\cache\dod-guard\quality-guard\037c77ae9669\skills\quality-refactor\scripts\quality-scan.mjs`,
as the scanner to run. This path is outside the repository entirely, so no
`.gitignore` rule in this repository covers it and `git check-ignore`
reports nothing for it. It names one specific user's home directory and one
specific installed plugin hash, `037c77ae9669`, that changes on every
`/plugin update`. A fresh clone on another machine, or this same machine
after the plugin next updates, has no file at that path. This is not a
git-ignore violation under the spec's literal wording, but it is a worse
break than either ignored case above: those two resolve themselves by
running a command in order, this one needs the path rewritten by hand
before the autopilot prompt can run at all.

Case 5. `scripts/quality-checklist.mjs` line 13 hardcodes the same absolute
plugin-cache path as case 4, as its `SCANNER` constant, used both in a
comment shown to a human and interpolated into the regenerate-checklist
instructions the script writes into `docs/notes/quality-checklist.md`.
Same reasoning as case 4: outside the repository, outside `.gitignore`'s
reach, and broken by the next `/plugin update` on the very machine that
wrote it, not only by a fresh clone elsewhere.

Case 6. `.codex/hooks.json` names `time.ps1` by the absolute path
`C:\Users\siriu\RustroverProjects\DeepSeekCustom\time.ps1`. Step 4.1 of
this change tracked `time.ps1`, so the file itself now ships with a clone
and `git check-ignore -v time.ps1` reports nothing (no rule matches; the
`.gitignore:4` rule step 4.1 removed is gone). The half of the problem
step 4.1 fixed was the file's absence. The half it left open is this one:
the hook command still names one machine's home directory and one
machine's repository location by absolute path, so a clone checked out
anywhere else, or under a different Windows username, has the tracked file
on disk but the hook still cannot find it. Fixing this for real means
making the hook command path-relative or resolving it at run time, which
`.codex/hooks.json` is on the leave-alone list for in this step.

Case 7. `.cargo/config.toml` sets `CMAKE` to the absolute path
`C:\Program Files\CMake\bin\cmake.exe`, so whisper-rs-sys's build script
finds a cmake with a Visual Studio generator instead of the MSYS2 one that
otherwise sits ahead of it on PATH. This path is absolute and outside the
repository, so no `.gitignore` rule in this repository covers it and
`git check-ignore` reports nothing for it. It differs from cases 4 and 5,
the plugin-cache paths, in that `C:\Program Files\CMake\bin\cmake.exe` is a
conventional install location that a machine with CMake installed is
likely to have, rather than one user's home directory and one plugin
install hash. So it is the mildest case in this list, but it is still a
machine assumption a fresh clone can fail on, and the section's own stated
rule is that every such case gets recorded.
